# Pagus (파구스 · 파주 로컬 맛집 지도) 프로젝트 가이드

> 저장소 공통 규칙은 [`../CLAUDE.md`](../CLAUDE.md)에서 상속된다(PR 없이 직접 머지, CI/CD 없음·로컬 검증).
> 이 파일은 `Pagus/` 프로젝트 고유의 스택·아키텍처·불변식·검증 규칙만 다룬다.

## 프로젝트 개요

Pagus는 CodeIgniter 4와 MySQL로 만드는 파주 로컬 맛집 지도 서비스다.

> 마을(Pagus) 속 진짜 맛집을 찾다, 파주 로컬 맛집 지도 파구스.

MVP 범위는 공개 맛집 지도·검색·상세, 인증 사용자 후기, 운영자 맛집 관리까지다. 추천 알고리즘, 결제, 예약, 주문, 광고 상품은 별도 요구가 없으면 구현하지 않는다.

## 응답 스타일

- 대화 응답에만 `caveman` 스타일을 적용한다.
- 코드, 주석, 문서, 커밋 메시지는 정상적인 한국어로 작성한다.

## 기술 스택

- **백엔드**: PHP 8.4+ / CodeIgniter 4
- **DB**: MySQL 8.0+
- **지도**: 외부 지도 SDK — 지도 표시·마커 상호작용에만 사용한다. 맛집 공개 여부·권한·후기 상태 같은 비즈니스 규칙은 서버가 최종 결정한다.

이 프로젝트의 PHP(CodeIgniter 4) 코드는 부모 저장소들의 전역 PHP 규칙
([`~/.claude/rules/code-style.md`](~/.claude/rules/code-style.md),
[`~/.claude/rules/security.md`](~/.claude/rules/security.md),
[`~/.claude/rules/testing.md`](~/.claude/rules/testing.md),
[`~/.claude/rules/api-design.md`](~/.claude/rules/api-design.md))을 그대로 따른다.

## 범위와 우선순위

- 이 디렉터리 안의 파일만 Pagus 작업 범위로 본다.
- 기존 CodeIgniter 4 구조와 공식 기능을 우선 재사용한다.
- 새 기능을 시작하기 전에 요구사항, 데이터 불변식, 책임 레이어, 영향받는 화면·데이터, 검증 방법을 짧게 정리한다.
- 작업 전에는 현재 브랜치·변경 사항·`.env`의 존재 여부·테스트 DB 설정을 확인한다. 기존 변경과 시크릿은 보존하며 값 자체를 출력하거나 복사하지 않는다.

## 분석·개발 시 Graft 사용

- 분석, 버그 조사, 개발 범위 파악을 시작할 때는 원본 파일을 직접 검색하거나 열기 전에 `graft ask "<작업 질문>" --source`로 관련 코드·설정·호출 지점을 확인한다.
- 모든 발생 위치를 찾아야 할 때는 `graft grep "<식별자>"`, 심볼 수정 전 영향 범위를 확인할 때는 `graft callers <심볼> --depth all`, 파일 API를 빠르게 훑을 때는 `graft skeleton <파일>`을 사용한다.
- Graft 결과가 누락되었거나 그래프가 없는 경우에는 그 사실을 기록하고, 가능하면 `graft build`로 갱신한 뒤 다시 확인한다. 그래프에 없는 신규 파일·생성 파일만 `rg` 등 원본 검색으로 보완한다.
- Graft 결과의 경로·라인 범위를 기준으로 최소 범위를 읽고 수정한다. 분석 결과만으로 실행·통합·UI 동작이 검증된 것으로 간주하지 않으며, 해당 작업에 맞는 실제 검증을 별도로 수행한다.

## 구조와 책임

- `app/Controllers`: Request 입력 수신·검증, 인증/권한 확인, Service 호출, 응답 반환
- `app/Services`: 맛집·후기 유스케이스와 트랜잭션
- `app/Models`: Query Builder를 통한 데이터 접근과 허용 필드
- `app/Database/Migrations`: 스키마 변경
- `app/Database/Seeds`: 재현 가능한 개발용 초기 데이터
- `app/Views`: 화면 출력. Model을 직접 호출하지 않는다.
- `public/`: 웹 document root. 업로드 파일과 비밀 설정을 두지 않는다.

## 핵심 불변식

- 공개 화면에는 `restaurants.is_published = 1`인 맛집만 노출한다.
- 위도는 `-90..90`, 경도는 `-180..180` 범위여야 한다.
- 카테고리·주소 등 필수 맛집 정보는 서버 검증을 통과해야 저장한다.
- 후기 작성자는 자신의 후기만 수정·삭제할 수 있고, 운영자는 검수 상태를 관리할 수 있다.
- 신고된 후기는 처리 전까지 공개하지 않거나 정책에 따른 상태 필터를 적용한다.
- 맛집과 후기의 삭제·숨김은 가능하면 soft delete 또는 상태 전이로 복구 가능성을 보존한다.
- 다중 테이블 쓰기는 Service 트랜잭션으로 감싸고 실패 시 전체를 rollback한다.
- 목록 조회에는 공개 상태 조건, 정렬, 페이지네이션을 명시한다.

## 데이터베이스 규칙

- 테이블·컬럼은 `snake_case`, 테이블은 복수형, PK는 `id`, FK는 `{단수}_id`를 사용한다.
- 외래 키와 자주 조회하는 필터·정렬 컬럼에 인덱스를 검토한다.
- SQL 문자열 직접 조합을 금지하고 Query Builder 또는 바인딩을 사용한다.
- 새 스키마는 migration으로 추가하고, 되돌림 가능성을 확인한다.
- migration을 추가·변경하면 빈 테스트 DB에서 적용하고, 해당 배치의 rollback 가능 여부를 확인한다. 데이터 보정이 필요하면 되돌림 정책과 백업·복구 방법을 함께 문서화한다.
- 운영 DB를 테스트에 사용하지 않는다. 테스트 전용 DB와 seed를 사용한다.
- 시각 데이터는 저장·세션 타임존 규칙을 확인한 뒤 일관되게 처리한다.

## 로컬 검증

- CI/CD가 없으므로 머지 전 아래를 **로컬에서** 순서대로 직접 실행해 확인한다.

```bash
composer check      # PHP-CS-Fixer dry-run + diff 공백 오류 검사
composer analyse    # PHPStan 정적 분석
composer test        # PHPUnit 단위 테스트
```

- 하나라도 실패하면 원인을 수정한 뒤 처음부터 다시 검증한다. 검증 실패 상태로 커밋하거나 push하지 않는다.
- 명령이 아직 정의되지 않은 초기 상태라면 `composer.json`의 실제 스크립트를 먼저 확인하고, 가능한 범위에서 `vendor/bin/phpunit`, migration 적용·rollback 점검, PHP 문법 검사를 수행한다.
- UI 변경은 실제 `http://pagus.test/` 화면에서 확인하고, 지도·검색·권한·공개 상태 필터의 성공·실패·권한 경계를 함께 검증한다.
- 외부 지도·지오코딩 API는 실제 호출 또는 명시적인 미검증 사유를 결과에 남긴다.

## 보안과 품질

- `$_GET`, `$_POST`, `$_REQUEST`, `$_FILES`를 직접 읽지 말고 CI4 Request와 Validation을 사용한다.
- POST·PUT·DELETE에는 CSRF 보호를 적용한다.
- 역할 권한은 서버에서 검사한다. 화면에서 버튼을 숨기는 것만으로 권한을 대신하지 않는다.
- 사용자 입력과 후기·주소 출력은 적절히 escape한다.
- 비밀번호는 `password_hash()`로 저장하고, 토큰·API 키·비밀번호를 코드·로그·커밋에 넣지 않는다.
- 업로드가 추가되면 확장자·MIME·크기 검증 후 웹 루트 밖에 저장한다.
- 지도·지오코딩 등 외부 API 호출에는 timeout과 실패 처리를 둔다.
- 새 기능·버그 수정에는 핵심 성공·실패·권한 경계에 대한 회귀 테스트를 추가한다.
